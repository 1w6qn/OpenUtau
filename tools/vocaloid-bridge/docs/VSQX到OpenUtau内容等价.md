# 给定 VSQX，OpenUtau 产出与 VOCALOID 编辑器相同的内容

> 目标：**同一个 .vsqx，OpenUtau 打开后工程内容应与 VOCALOID 编辑器里的内容一致。**
> 现状：音符/速度/拍号**已经一致**；**音高曲线不一致**（内置读取器把它缩放了、并且抹平了），9 个音符级调教参数则根本无对应物。
> 工具：scripts/openutau_vsqx_import.ps1（无界面跑 OpenUtau 自己的读取器）+ scripts/vsqx_equivalence.py（audit / apply）。测试：tests/test_vsqx_equivalence.py（7 例）。
>
> **修订（PBS 模型）**：本文早先按“固定每单位音分”估算，结论偏悲观。实测与源码（V4ScoreWriter.cs：S=PBS、P=PIT）表明音高应由 **音分 = P / 8192 × (S × 100)** 计算，S 逐音符变化。改为 PBS 后：内置导入的误差中位只有 **4–5 音分**（斜率约为目标的 1.38 倍），修正后 **0.0 音分**；截断率从 3–5% 降到 0–0.1%。WAV 层面的结论见 [WAV一致的条件](WAV一致的条件.md)。

## 0. 结论速览

---

## 1. “相同内容”指什么

| 内容 | 可表示 | 判定 |
| --- | --- | --- |
| 音符位置 / 长度 / 音高 | ✅ | 逐音符相等 |
| 歌词 / 音素 | ✅ | 歌词相等；源里的 - 变成 OpenUtau 的休止标记 +~，算规范化、需记录 |
| 速度表 / 拍号表 | ✅ | 逐点相等 |
| 音高曲线（P → PITD） | ✅（不同单位） | 需声明单位因子后逐点相等 |
| accent / decay / bendDep / bendLen / risePort / fallPort / opening / vibLen / vibType | ❌ | OpenUtau 无对应参数，只能报告 |
| 声库、授权、引擎专用效果 | ❌ | 跨软件不可能 |

所以“相同”必须先定义单位：VOCALOID 的 P 是“弯音单位”，OpenUtau 的 PITD 是“音分”。**本工具要求显式给出因子**（--pitch-unit-cents，默认 2400/8192 约 0.293），而不是偷偷假设。

## 2. 怎么测、怎么修

```powershell
# 1) 用 OpenUtau 自己的读取器把 .vsqx 导入成 .ustx（无界面、独立数据目录、不改用户设置）
pwsh -NoProfile -File scripts\openutau_vsqx_import.ps1 -Source song.vsqx -Output song-native.ustx

# 2) 对比“OpenUtau 的产出”与“VSQX 的内容”
.\.venv\Scripts\python.exe scripts\vsqx_equivalence.py audit --source song.vsqx --target song-native.ustx

# 3) 用 P 曲线重写 PITD，再复测
.\.venv\Scripts\python.exe scripts\vsqx_equivalence.py apply --source song.vsqx --target song-native.ustx --out song-equal.ustx
```

audit 退出码 1 表示存在不可解释的差异（音高误差 > 1 音分、歌词差异非休止规范化、轨数不等）。

openutau_vsqx_import.ps1 直接调用 OpenUtau.Core.Format.VSQx.Load 与 Ustx.Save，数据目录指向 tmp\openutau-vsqx-import，不读写用户设置、不启动 GUI。

## 3. 实测（five-voices.vsqx：5 轨 644 音符，P 曲线 54k 点）

| 轨道 | 音符/位置/音高 | 歌词 | 内置导入相关系数 | 内置导入斜率 | 内置导入误差中位 | 修复后相关系数 | 修复后斜率 | 修复后误差中位 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 主唱 | 247/247 全等 | 244/247（3 休止） | 0.879 | 0.083 | 43 音分 | **0.997** | **0.2928** | **0.2 音分** |
| 高和声 | 224/224 | 224/224 | 0.907 | 0.068 | 57 音分 | **0.998** | **0.2928** | **0.2 音分** |
| 中和声 | 116/116 | 105/116（11 休止） | 0.828 | 0.062 | 68 音分 | **0.996** | **0.2928** | **0.2 音分** |
| 低和声 A | 35/35 | 34/35 | 0.966 | 0.090 | 38 音分 | **0.998** | **0.2928** | **0.3 音分** |
| 低和声 B | 22/22 | 21/22 | 0.910 | 0.086 | 45 音分 | **0.999** | **0.2926** | **0.2 音分** |

- 期望斜率就是 --pitch-unit-cents 默认的 0.293；修复后实测 0.2926–0.2928，说明写入与读回一致。
- 截断（超出 ±1200 音分）：3.4%–4.6%，修复前后相同——这是 OpenUtau 表达范围决定的，不能靠换算消除。
- 速度/拍号：直接相等（本工程 128 BPM、4/4，无前导小节偏移）。
- 9 个调教参数：本工程全部是默认值（0 个音符带非默认调教），所以“不可表示”计数为 0；换一个真调教过的工程，计数会直接告诉你丢了多少。

## 4. 为什么会不一致：内置读取器的 P 换算

用“真实工程 + 人工替换 P 曲线”的受控实验（其它内容全部不动）：

| 输入 P（常数） | 内置导入后的 PITD |
| --- | --- |
| 4000 | 733 |
| ±4000（交替） | ±733 |
| 0 → 8000 线性 | 0 → 1200（到顶截断） |

结论（✅ 实测）：OpenUtau 0.1.574 的内置读取器把 P 换算成音分时用的是 **约 0.1832 音分/单位**（733 除以 4000），再**截断到 ±1200**；对真实曲线还做了平滑，所以同一条曲线上的回归斜率只有 0.06–0.09、中位误差几十音分、颤音被抹平。

这既不是本工具默认的 0.293（24 半音灵敏度），也不是“1:1 当音分”。**三种约定都只是约定，最终必须用 VOCALOID 引擎的实际出声来标定**（见第 6 节），这也是 --pitch-unit-cents 必须显式给出的原因。

## 5. 边界

1. **PITD 范围 ±1200 音分**：超出部分只能截断并计数（本工程 3.4%–4.6%）。要完全保留，只能改音符或在 OpenUtau 里调整表达式范围后再写。
2. **9 个调教参数不可表示**：工具只统计与报告，不伪造。
3. **休止标记**：源里的 - 变成 +~ 是 OpenUtau 的合法表示，工具把它计为“规范化”而非错误。
4. **只覆盖 VSQX4**：V3 的 posTick 结构与 V4 不同（VSQx.Load 里两条路径），当前解析器不支持。
5. **单位因子未标定**：默认 0.293 是“24 半音灵敏度”约定；不是从 VOCALOID 出声反推的结果。

## 6. 下一步：把“约定”变成“标定”

用 plugins/vocaloid-bridge 的 V4 后端渲染一个**只含常数 P** 的极小 VSQX（例如 P=341 覆盖一个长音），测出实际 F0 偏移（音分），即可得到 k_VOCALOID = 偏移 / 341。有了它：

- --pitch-unit-cents 用标定值，audit 的“期望斜率”才对得上 VOCALOID 的真实行为；
- 再把 OpenUtau 渲染出的 PCM 与 VOCALOID 渲染的 PCM 做逐帧 F0/能量对齐（scripts/measure_fidelity.py 的口径），才算真正闭环。

在此之前，本工具能保证的是：**工程内容层面（音符/歌词/速度/拍号/曲线形状）与 VSQX 一致，且在声明的单位约定下逐点误差 ≤0.3 音分**。
