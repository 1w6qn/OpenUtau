# 实时渲染：同一 VOCALOID 声库、同一轨道，在 OpenUtau 里实时出同样的声音

> 目标：同一声库、同一条轨道，OpenUtau 实时播放出的音频与 VOCALOID 编辑器的渲染结果一致。
> 结论：**引擎侧已实测可行**——单帧合成耗时只有预算的 1/60 左右，节流到实时播放时产出的 WAV 与批量渲染**逐字节一致**。OpenUtau 侧还差“把引擎挂进播放栈”这一步（设计见第 4 节）。

---

## 1. 实时渲染是什么、不是什么

VOCALOID 引擎本来就是**逐帧增量**的：V4 的 DSE 每次调用 DSEDoStepSynthesis 合成 **256 样本**（44.1 kHz → 5.805 ms）就返回，编辑器正是靠这个接口做实时预览。

所以“实时”= 以引擎的帧节奏持续调用它，把 PCM 送进音频环；**不是**“先渲完整句再播放”（当前 bridge 的默认做法）。

## 2. 实测：帧耗时与实时余量

同一段 8 音符、8.25 秒的请求（V4 引擎 + 4:1 声库），2025 帧：

| 指标 | 非节流（尽可能快） | 节流到实时 |
| --- | --- | --- |
| 每帧预算 | 5.805 ms | 5.805 ms |
| p50 | 0.031 ms | 0.062 ms |
| p99 | 0.514 ms | 1.056 ms |
| 最大 | **1.158 ms** | 11.99 ms（系统调度抖动一次） |
| 总墙钟 | 0.255 s | **11.77 s**（音频 11.755 s） |
| 实时因子 | **0.016（约 61× 余量）** | 1.001（跟得上） |
| 输出与批量渲染 | 参考 | **逐字节一致（null -240 dB）** |

关键结论：
1. **实时可行**：最坏帧 1.16 ms 也远低于 5.805 ms 预算；
2. **实时 = 离线**：节流只是插入 sleep，不改变引擎调用序列，所以输出逐字节相同（已用 wav_compare 验证）；
3. 偶发 12 ms 尖峰是 Windows 调度抖动，用 8–16 帧抖动缓冲即可吸收。

## 3. 延迟预算

| 组成 | 取值 | 说明 |
| --- | --- | --- |
| 引擎帧 | 5.805 ms | 256 样本 |
| 抖动缓冲 | 8–16 帧 = 46–93 ms | 吸收调度尖峰（无缓冲时 12 ms 尖峰就会爆音） |
| 事件预读 | 1–2 帧 | 音符/曲线必须提前于播放头送入引擎 |
| 合计端到端 | **约 60–110 ms** | 与 VOCALOID 编辑器的实时预览同量级 |

## 4. 接入 OpenUtau 需要的三段改动（尚未完成）

1. **AudioSource**：在 fork 里实现一个 OpenUtau 音频源，向播放栈持续提供 PCM；内部线程按 5.805 ms 节奏调用 host 的流式接口，写入环形缓冲。
2. **事件预读**：把“播放头 + 缓冲长度”作为合成前沿，把音符、PBS、音素、PITD 曲线在前端一次性量化成引擎事件（等价于现在 V4ScoreWriter 生成的 Daisy 流），避免播放中反复重建。
3. **编辑失效**：任何影响引擎输入的操作（音符、歌词、曲线、切换声库）→ 标记 dirty 区间 → 后台重渲并替换环内数据；播放头进入未就绪区间时回退到上一份缓存。

现在的 native_render_probe.ps1 加环境变量 SVS_STREAM_PACE=1 已经是这套时序的**最小原型**：它证明节流驱动引擎不会改变输出。

## 5. 复现命令

```powershell
# 非节流：测每帧成本（写出 stats json）
$env:SVS_STREAM_STATS='tmp\wav\stats-unpaced.json'
pwsh -NoProfile -File plugins\vocaloid-bridge\tests\native_render_probe.ps1 -Config plugins\vocaloid-bridge\vocaloid4.example.json -Request tmp\wav\req-pbs.json -OutputWavPath tmp\wav\stream-unpaced.wav

# 节流到实时：墙钟应≈音频时长
$env:SVS_STREAM_PACE='1'
$env:SVS_STREAM_STATS='tmp\wav\stats-paced.json'
pwsh -NoProfile -File plugins\vocaloid-bridge\tests\native_render_probe.ps1 -Config plugins\vocaloid-bridge\vocaloid4.example.json -Request tmp\wav\req-pbs.json -OutputWavPath tmp\wav\stream-paced.wav

# 两者必须逐字节一致
.\.venv\Scripts\python.exe scripts\wav_compare.py tmp\wav\stream-unpaced.wav tmp\wav\stream-paced.wav
```

实现位置：V4/NativeSynthesis.cs（逐帧计时 + 可选节流）、V4/NativeHost.cs（环境变量开关与统计上报）。

## 6. 边界

- 实时能力结论建立在**本机 V4 引擎 + 4:1 声库**；V5/V6 AI 声库只有离线 part.Render，实时路径未验证。
- 目前只证明“引擎能实时、实时结果=离线结果”，**尚未**把该数据源接入 OpenUtau 的播放与编辑闭环。
- 长句/整曲的实时可行性取决于事件流长度与内存；本工程单轨 8 音符已验证，整曲需再做一次压力测试。

## 7. 流式 host（已实现）与 seek 精确性

新增独立流式宿主：\`V4/stream/StreamHost.cs\` + \`V4/run-stream-host.ps1\`（复用 \`NativeApi\`/\`NativeSynthesis\`/\`V4ScoreWriter\`/\`NativeFrontend\`），支持：

- **按帧窗口**：\`-StartSeconds f<帧号> -Seconds f<帧数>\`（也接受秒），从任意位置开始合成；
- **节流**：\`-Pace\` 按 256 样本帧的墙钟节奏输出；
- **统计**：每帧 p50/p99/max、late_frames、实时因子、墙钟时长。

实测（8 音符 / 11.755 秒请求，2025 帧）：

| 实验 | 结果 |
| --- | --- |
| 非节流整段 | 0.357 s 渲完 11.755 s 音频（实时因子 0.028） |
| 节流整段 | 墙钟 11.77 s ≈ 音频时长，跟得上 |
| 从 3.001 s 起渲 1 秒窗口 | 与整段渲染对应切片**逐样本相同**（max|diff| = 0） |
| 5 个连续 172 帧窗口（节流）拼接 | 与整段前 220160 样本**逐样本相同**（identical = true） |

也就是说：**seek 与窗口化不会改变音频**——引擎状态由“从 0 合成到窗口起点”保证，窗口只是不收集前面的样本。

复现命令：

¶¶¶powershell
# 整段（float32 WAV）
pwsh -NoProfile -File plugins\vocaloid-bridge\V4\run-stream-host.ps1 -Config plugins\vocaloid-bridge\vocaloid4.example.json -Request tmp\wav\req-pbs.json -Output tmp\wav\full-float.wav -StartSeconds 0 -Seconds 12

# 从第 516 帧开始、渲 172 帧，节流
pwsh -NoProfile -File plugins\vocaloid-bridge\V4\run-stream-host.ps1 -Config plugins\vocaloid-bridge\vocaloid4.example.json -Request tmp\wav\req-pbs.json -Output tmp\wav\win.wav -StartSeconds f516 -Seconds f172 -Pace
¶¶¶

接入 OpenUtau 时，\`IAudioSource\` 只需要按帧号连续请求窗口（上一窗口的帧号 + 帧数），把 PCM 写入环形缓冲即可；上面的“窗口拼接 = 整段”就是这条路径的正确性证明。


## 8. 常驻帧服务器（已实现，OpenUtau 只需薄客户端）

\`V4/stream/StreamServer.cs\` + \`V4/run-stream-server.ps1\`：进程常驻，持有同一个已加载乐句与引擎实例，按帧号服务窗口。

协议（每行一条命令；\`read\` 的回复 = 一行 JSON + 恰好 \`samples*2\` 字节 int16 LE PCM）：

| 命令 | 回复 | 说明 |
| --- | --- | --- |
| （启动） | \`{ready, sample_rate, frame_size, total_frames, budget_ms}\` | 句首一行 |
| \`{"op":"seek","frame":N}\` | \`{frame, preroll_ms}\` | 重建引擎实例并预跑到 N 帧 |
| \`{"op":"read","frames":M,"pace":true}\` | 一行 JSON + PCM | 顺序读取 M 帧，可按墙钟节流 |
| \`{"op":"ping"}\` / \`{"op":"close"}\` | \`{pong}\` / \`{closed}\` | 存活检查 / 退出 |

实测（\`tests/stream_server_probe.py\`，8 音符 / 11.755 秒 / 2025 帧）：

| 性质 | 结果 |
| --- | --- |
| 5 个连续 172 帧窗口拼接 vs 整段渲染 | **逐样本相同**（220160 样本，identical = true） |
| \`seek 516\` 后读 172 帧 vs 整段切片 | **逐样本相同**（预跑 28.9 ms） |
| 节流读取 5 窗口 | 墙钟 **5.000 s** vs 音频 4.992 s（比值 1.002） |

关键实现细节（踩过的坑，写进代码注释）：

1. **seek 必须重建 DSE 实例**：引擎在 Start/Stop 之间保留声部状态，只重建 FrameStream 会得到与整段渲染不同的采样；实测必须 \`DSEDelete\`+\`DSECreate\`+\`DSESetStaticSetting\` 后预跑。
2. **节流必须用进程级时钟**：按“本窗口渲染耗时”累计会线性膨胀（实测 5 秒音频被拖成 15 秒）；改成从 seek 起算的单一 Stopwatch 后比值回到 1.002。
3. **顺序读取不需要重新合成**：\`FrameStream\` 保存了 DSCL 事件游标与 DSE 帧号，窗口之间直接续跑，所以第 N 秒的窗口成本与位置无关。

OpenUtau 侧薄客户端示意：

¶¶¶text
1. 启动 run-stream-server.ps1（config + request），读首行 ready
2. seek(播放头帧)
3. 循环：read(frames = 缓冲帧数, pace = true) → 追加到 ring buffer → 播放
4. 播放头前进时按帧号连续 read；编辑后 seek(受影响区间起点)
